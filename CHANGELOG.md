# Changelog

All notable changes to `web-router` are recorded here, newest first. Versions
follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html); while on
`0.x`, a breaking change bumps the minor version.

## [Unreleased]

### Added

- `WebRouter.plan(prompt, budget=, tool=)` and `run(plan_or_prompt, budget=, tool=)`, sync and async (experimental): prompt-level routing. `plan` runs nothing: it finds the `http(s)` URLs in the prompt, builds every method's candidates, asks the attached router and merges its answer, and returns a `Plan` -- the method (search, extract, answer, research or browse; `search` with no router unless `tool` pins one), its options (`query`, `urls`, or `task` and `start_url`, plus research's budget-mapped effort) and its backends in order, with the decision record. `run` calls that method on `auto` in that order and returns its own response with the record on it; `run(prompt)` does both. `url_policy="public_only"` on `WebRouter` and `AsyncWebRouter` (off by default) refuses loopback, link-local, cloud metadata, private, shared and reserved hosts -- decimal, hex, octal, short, IPv4-mapped and full-width spellings included, and any URL a browser could read another host from (a backslash, `@` or `%` in the authority, whitespace or a control character) -- in a plan's URLs before any candidate is built, and in URLs a router supplies; each refusal is in the record's `dropped` by scheme and host. It is a hostname check before dispatch: it resolves no DNS and follows no redirect. With no policy a router may now supply any `http(s)` URL. `plan(tool="extract")` raises `MissingParameterError` when it has no URL to fetch, none found or every one refused, rather than return a plan `run` could not execute.
- A routed call is now shown the candidates `build_candidates` finds on the chain it runs on -- each priced and timed, those the budget leaves out named in the record's `dropped` -- and the router's answer is applied by the merge rule: its exclusions, its options for the method (sent with the call, recorded in `params`), and, for research with no effort from the router or the caller, the effort the budget maps. A malformed decision is `router_invalid` by the same check the merge rule makes, and `router_timeout` is recorded only when the router ran out of time.
- `web_router.routing.pricing` (experimental): the one rule for what an attempt is estimated to cost and take, which the budget's ledger, the candidate builder, the effort mapping and the merge rule's `search_depth` check all read. A floor row (`estimate_is_floor`) and a request with `provider_options` are unpriced everywhere, with or without a cost cap, and research's p90 comes from the effort table where the price list has none.
- `web_router.routing.candidates.build_candidates()` (experimental): every (tool, provider) a call could be routed to -- the members of each method's `auto` chain, a configured `chain` included, that map every option the request sets -- each with its estimated cost from the price list and its measured p90 latency, `None` where unknown. A budget prefilters them: under a cost cap an unknown price or an estimate over what is left drops a candidate (research is priced at the `effort` set, else at the one `map_effort` picks for that backend under the budget, and a request with `provider_options` counts as unpriced, since they can change the billed mode); under a time cap a known p90 over the time left drops one, and an unknown p90 only when `strict`. Each drop is returned with its reason, and the candidates no measurement backs are listed. Nothing calls it yet.
- `router=`, `route_tools=` and `fail_on_router_error=` on `WebRouter` and `AsyncWebRouter` (experimental): attach a router -- a function or coroutine function, or an object with `route(req)` or `aroute(req)` -- that orders `auto`'s backends for search, extract, answer, research and browse (all five unless `route_tools` names fewer). It is asked only when a call goes to `auto`, sees the `RouteRequest` (the prompt and `tool:provider` candidates, no key values), and has 50 ms unless it declares `timeout_s`, cut to the call's time left; a sync router runs on a worker thread and is dropped, still running, at its deadline, and an async one called from sync code runs on a private loop thread, as does the coroutine a decorated async router hands back; an async call cancelled while it waits cancels the router too. A router that raises, cancels itself, runs out of time or answers something other than a `RouteDecision` leaves the static order, recorded in the response's `decision`; `fail_on_router_error=True` raises `RouterError` instead. A string, a class or any other value raises `ConfigurationError`. With no router, calls run as before.
- `web_router.routing.candidates.build_candidates()` (experimental): every (tool, provider) a call could be routed to -- the members of each method's `auto` chain, a configured `chain` included, that map every option the request sets -- each with its estimated cost from the price list and its measured p90 latency, `None` where unknown. A budget prefilters them: under a cost cap an unknown price or an estimate over what is left drops a candidate (research is priced at the `effort` set, else its default, and a request with `provider_options` counts as unpriced under a cost cap and untimed under a time cap, since they can change the billed mode). A chain member `auto` could not build -- no credential and no keyless tier, or a missing extra -- is never a candidate; under a time cap a known p90 over the time left drops one, and an unknown p90 only when `strict`. Each drop is returned with its reason, and the candidates no measurement backs are listed. Nothing calls it yet.
- `web_router.routing` (experimental), the router contract: `ToolName`, `Budget(max_cost_usd, time_limit_s, strict)`, `Candidate`, `RouteRequest`, `RouteDecision` and `Plan`, frozen keyword-only dataclasses exported from `web_router`, and `DecisionRecord` (with `DecisionHop` and `DecisionAttempt`), a pydantic model in a new `decision` field on `SearchResponse`, `ExtractResponse`, `AnswerResponse`, `ResearchResponse` and `BrowseResponse`, `None` until a call is routed or budgeted. `search`, `extract`, `answer`, `research` and `browse` take `budget=`, sync and async; it is accepted and not yet enforced, so a call with a budget answers as one without.
- `web_router.routing` (experimental), the router contract: `ToolName`, `Budget(max_cost_usd, time_limit_s, strict)`, `Candidate`, `RouteRequest`, `RouteDecision` and `Plan`, frozen keyword-only dataclasses exported from `web_router`, and `DecisionRecord` (with `DecisionHop` and `DecisionAttempt`), a pydantic model in a new `decision` field on `SearchResponse`, `ExtractResponse`, `AnswerResponse`, `ResearchResponse` and `BrowseResponse`, `None` until a call is routed or budgeted. `search`, `extract`, `answer`, `research` and `browse` take `budget=`, sync and async.
- Per-call budgets are enforced (experimental). `budget=Budget(max_cost_usd=, time_limit_s=, strict=)` on `search`, `extract`, `answer`, `research` and `browse` checks each attempt before it starts -- each `auto` member in order, or the one backend named -- against what is left. Money is the estimated list price from `web_router.prices`, an extract's per URL, and an attempt that fails is still charged; under a cost cap a candidate whose price is unknown is skipped, never guessed: no row, `unknown`, billed by tokens, a row marked `estimate_is_floor` (a new `Price` field, set where charges are billed on top: Brave's answer, Browser Use's browse), or a request carrying `provider_options`, which can change the mode billed. Under a time cap the call runs under the per-call deadline, a candidate whose measured p90 does not fit the time left is skipped, one with no measured p90 runs within the deadline unless `strict=True` drops it, and research and browse wait at most `min(timeout, time left)`, then raise their own timeout error with the job's handle: the cap limits the wait, not what the job spends. A call where every candidate was skipped raises `BudgetExceededError` (importable from `web_router`), naming each skip and why; `auto` never falls back on it. The response's `decision` carries the estimated spend (`estimated_cost_usd`, `cost_is_estimate`), every attempt and every skip. With no budget nothing changes.
- `web_router.prices` (experimental): the estimated list price of every (provider, method, mode) web-router calls, shipped as `web_router/data/prices.json`. `estimate(provider, method, mode=None)` returns the cost in US dollars of one request, page, run or browser-minute, and `None` when the vendor publishes no price, bills by tokens, or the mode has no row; `price()` returns the whole row (`unit`, `note`, `source_url`, `checked`, and measured latency) and `prices()` every row. A mode is the `search_depth` or `effort` value, or a vendor mode written `:name`; unset, it is the call that sets none. `benchmarks/providers/PRICING.md`'s tables are now generated from the same file with `make prices`.
- `benchmarks/providers/frozen/`: the per-question results route-eval and the latency priors rest on, committed so a fresh clone has them -- `sealqa-hard-254`, its rerun `sealqa-hard-254-twin`, `simpleqa-300-v2` with Keenable and DeepSeek on the same questions, and `answer-simpleqa-300`, one gzipped JSON line per question and backend with `question_id`, `provider`, `method`, `mode`, `grade`, `latency_s`, a stated `cost_usd` and an error class, and a `manifest.json` and `SHA256SUMS` beside them. No question, answer or vendor message text is committed: `uv run --all-extras python benchmarks/providers/frozen.py join` checks the checksums and puts each question, its gold answer and its labels back from the public SimpleQA and SealQA. Experimental until 1.0.
- Measured latency in the price list (experimental): every search and answer row the frozen results cover carries `latency_p50_s` and `latency_p90_s`, the median and 90th-percentile seconds of the calls that succeeded, with `latency_n`, the runs pooled (`latency_runs`) and the newest run's date (`latency_measured`). Every set that covers a row is pooled, except a rerun of another set's questions (`sealqa-hard-254-twin`) and a mixed set (`tools-effort-60`, whose answer rows are copies), so no question counts twice. `prices.estimate_latency(provider, method, mode=None)` returns `(p50, p90)`, and `None` where nothing measured it: extract, research, browse and the modes the scans did not run. `make latency` rewrites the fields from `benchmarks/providers/frozen/`, and a test fails while they are stale.
- A per-call deadline under every method, the mechanism a per-call budget will build on (experimental; no public parameter sets it yet). Under one, search, extract, a template run and answer stop at the deadline and raise `DeadlineExceededError` (importable from `web_router`), naming it; an extract keeps the pages that came back in time and lists the rest in `failures`. Every request is clamped to the time left -- the HTTP base, the keyless MCP backends, the Nimble and Tavily SDKs -- and nothing changes without a deadline. `auto` tries a next member only while time is left and holds none back for later ones. Research and browse wait no longer than the deadline and raise their own timeout error with the job id; the call that submits a billed run is clamped as before and never cut short for a later member.
- `benchmarks/providers/tools_effort.py` (experimental): the tool and effort set -- 60 questions from SimpleQA, SealQA Seal-Hard and FRAMES, some given their pages, each through search then read, extract, `answer()` and `research()` at each effort, graded by the same judge as the frozen sets. `--budget` (default $125) is a hard cap: each row reserves its worst case before it starts, and a row that would pass the cap is refused; a call is charged its stated cost, else its list price from `web_router.prices`, else a fallback written in the script, never $0, and the judge counts too. Rows are appended as they finish, so running the command again resumes. `--dry-run` prints the plan and its cost and calls nothing. `frozen.py` learns a `mixed` set, whose rows name their own method, so a finished run freezes with `build` and comes back with `join`. Its first run is frozen as `benchmarks/providers/frozen/tools-effort-60.jsonl.gz`: 60 questions, 1,150 rows, most of its Perplexity research rows failed during the run (`failed_rows` in the manifest counts every failed row).
- `benchmarks/providers/route_eval.py`, route-eval: replays a router over the frozen results, offline, and scores it against today's static order -- accuracy, mean cost (an unknown price stays unknown), mean latency, regret against the oracle and the static order, fallbacks and the router's own overhead, in-sample and held out on one seeded split, read against the noise floor of the SealQA twin run. A router is `static`, `oracle`, `always:<backend>` or your own `(prompt, candidates)` callable; v1 covers provider order for `search` and `answer`. Experimental until 1.0.
- route-eval scores tool choice and research effort on `tools-effort-60` (experimental): a candidate there is a path, `method:backend[:mode]` such as `research:parallel:low`, ranked through the same `(prompt, candidates)` interface. The static yardstick is today's default, search then read through `auto`'s order; the oracle is the right path, cheapest then fastest. The set's report ends with each research backend's accuracy, cost and latency by effort, with the rows that failed during the run on a rate-limit or quota error left out and counted, and `tools-effort-60` joins the default sets.
- `web_router.routing.params.map_effort(provider, budget, effort=None)` (experimental): the research effort a budget picks. Under a cost or time cap it returns the cheapest measured effort whose accuracy is within route-eval's noise floor of the most accurate one that fits, read from `web_router/data/efforts.json` (`make efforts`, generated from `tools-effort-60`; a test fails while it is stale) and the price list. An effort with no known price never fits a cost cap; one with no known p90 fits a time cap unless the budget is `strict`. A backend with fewer than two measured efforts keeps its default, marked unmeasured, and an effort the caller set always stands, with `misfit` saying when it does not fit. With no budget nothing changes. Only research's effort is mapped; search keeps its own `search_depth` and `max_results`. Nothing calls it yet.
- `web_router.routing.merge.merge(request, decision, static_order, *, failure=None, caller_set=(), url_check=None)` (experimental): the merge rule, a pure function that turns a router's `RouteDecision` into one method, an ordered list of backends and checked options (`Merged`, with `MergeNotes` and `record()` for the decision record). The method is the pinned one, else the router's first with a candidate left, else `search`, and a fallback never moves to another method; the router's ranking comes first, then the static order; only `exclude` removes a candidate, and never the last one; an unknown id is dropped and noted; a router may set only `max_results` and `search_depth` on search, `effort` on research, and URLs on extract and browse through a URL policy, never one the caller set, and an `effort` or `search_depth` that does not fit the budget on every backend in the order -- an unknown price never fits a cost cap -- is dropped and noted, and so is one a backend in the order does not take; a timeout, an exception or a malformed decision gets the static order with `router_timeout`, `router_error` or `router_invalid`, and a decision that decides nothing gets it recorded as `router_empty`, not a failure; extract with no URL searches instead. A URL a router sets is never shown whole in the record, the notes or the `repr`: only its scheme and host. Nothing in the library calls it yet.

### Changed

- `PageState`, `PageSnapshot`, `Screenshot`, `PageLoadState` and `PageFormat` move from `web_router.types` to `web_router.types_page`. `from web_router import ...` works as before; an import from `web_router.types` must change.
- `auto`'s default `search` (keyed) and `answer()` orders are now generated by `make chains`, ranked by accuracy on the frozen `sealqa-hard-254` and `answer-simpleqa-300` sets (method in `benchmarks/providers/README.md`). Search: perplexity, nimble, webiq, linkup, tavily, exa, parallel, brave, you (was perplexity, nimble, linkup, tavily, brave, webiq, parallel, exa, you). Answer: perplexity, you, linkup, parallel, exa, brave (was perplexity, exa, you, linkup, parallel, brave). The previous search order came from a SimpleQA scan; search is now ranked on SealQA hard because on SimpleQA every keyed backend scores 81-95%, too close to tell them apart, while on SealQA hard they differ. With every key, Perplexity still serves first; with some, another may, and some cost more: with Brave and Exa keys, a search now goes to Exa ($0.017) before Brave ($0.005). Keep the old order with `provider_config={"auto": {"chain": {...}}}`.
- The provider scan's recommended order now uses route-eval's ranking: within the noise floor the cheaper backend at list price goes first, and the keyless tier last.
- route-eval's held-out verdict now needs the static order outside the router's 95% interval as well as a margin wider than the noise floor, so one question on a 30-question half is no longer a gain or a loss.
- Contributors: `make check` now limits size. Ruff holds a function to 50 statements (`PLR0915`) and a complexity of 10 (`C901`); the few over either today carry a `noqa`. `tests/test_shape.py` holds a file to 400 lines, test files included; files already longer are listed in `tests/shape_baseline.json` and may only shrink, and `make shape-baseline` records a shrink and refuses a new or grown entry. `CHANGELOG.md` merges with git's union driver, so parallel pull requests that each add a line no longer conflict.
- route-eval ranks each method with its own noise floor, the spread of its own rerun, where one is frozen, else with search's, and names the floor: each set's report says which, and `chains.json` gives each method a `noise_floor` (`value`, `measured_on`, `rerun`, `fallback`) in place of the one top-level figure. Only search has a rerun today, so `answer` and `tools-effort-60` are ranked with search's 1.2 points, as before. A backend or path counted on fewer than 20 questions is no longer ranked: it is listed after the ranked ones as *too few questions* (`too_few_questions` in the summary and in `chains.json`, beside a top-level `min_questions`). On `tools-effort-60` that is `extract:nimble` (10), `research:perplexity:low` (4) and `research:perplexity:medium` (19). The search and answer orders are unchanged.
- route-eval replays through the library's merge rule. A router of your own now takes a `RouteRequest` and returns a `RouteDecision` (or `{"decision": ..., "cost_usd": ...}`), in place of `(prompt, candidates)` returning ids; on `tools-effort-60` it chooses the method, the backends and research's effort. An id that is not a candidate is dropped and the rest of the ranking kept (it used to void the whole ranking), the candidates a router left out follow in the static order (the replay used to stop at the end of the ranking), and a failed attempt is charged its estimated cost (it used to cost nothing). On the frozen sets the static, oracle and default routers score as before: none of them walks past a failed row.
- `chains.json`'s per-backend `account_failures_left_out` is renamed `rate_limit_or_quota_left_out`, for the error classes it counts. The file is experimental; every value is 0 and the orders are unchanged.

### Removed

- The decider spike: `WebRouter(decider=, decider_config=)`, `WebRouter.classify()`, `WebRouter.execute()`, `Route` and the `web_router.decisions` package (`DecisionProvider`, `register_decider()` and the `keywords`, `jev` and `llm` deciders). It was a proof of concept for routing, and a router contract will replace it. To keep using it, pin `web-router==0.9.0`, the last version that has it.

## [0.9.0] - 2026-11-04

### Added

- `Template.samples`: the runs a backend recorded for a template, each a `TemplateSample` (importable from `web_router`) with the `input` it accepted and the `output` record it returned -- the shortest route to a first run of a template you have not run before. Nimble publishes one per template, and its catalogue rows carry the published version whole, so a `templates()` page describes each template as fully as `template()` does, schemas and samples included. The MCP `template` tool returns `samples` beside the schemas, whole or not at all, as the schemas go; a listing row from `templates` now carries `required_inputs`, the schema's own `required` list, and `sample_inputs`, the first recorded input that names any, left out whole when it is too large for the listing, so a URL-keyed template is told from an id-keyed one without a second call. `run_template`'s description says what a run bills: one template run on the vendor's account, on Nimble at one flat rate for every template, with the dated figure in `benchmarks/providers/PRICING.md` and never in code.
- `answer()`, a seventh method, and its async twin: `WebRouter.answer(query, provider=...)` asks one question and returns the backend's own written answer with the sources it rests on, in one call -- between `search()`, which returns pages, and `research()`, a job of minutes. `AnswerResponse` carries `answer`, `citations` (the shared `Citation`; an inline marker in the answer goes in `field`), `outcome` (`partial` only when the backend says it stopped early), `request_id` and `raw`, one payload per call. An empty answer is returned as `""`, never raised. The options are `include_domains`, `exclude_domains`, `country`, `locale` and `recency` (`day`, `week`, `month` or `year`); a backend refuses each one it does not map with `UnsupportedParameterError`, before anything is sent. With `provider` unset the router's default serves the call when it is an answer backend, else the one configured answer backend, and a key passed in `provider_config` counts, and otherwise it raises `NoAnswerProviderError`, a `ProviderNotFoundError`, naming the configured backends when there are several and the variables to set when there are none. On the usual default, `auto`, that is answer()'s own `auto`: every answer backend you hold a key for, cheapest first at list price (Perplexity, Exa, You.com, Linkup, Parallel, then Brave). A backend that does not map an option the request sets is passed over without being built, one that refuses a value before sending or fails or answers with nothing is passed over for the next, each one tried bills, and with no key it raises `NoAnswerProviderError` naming the variables to set. `provider_config={"auto": {"chain": {"answer": [...]}}}` sets the order, and `fallback_on_empty=False` returns the first answer, empty or not. `AnswerProvider` and `HttpAnswerProvider` to add a backend, `register_answer_provider()`, `available_answer_providers()` and `configured_answer_providers()` beside the other registries, and an `answer` extra, which `mcp` and `all` include.
- `benchmarks/providers/answer.py`, the answer scan: every configured answer backend on the same questions as the search scan, each backend's own answer graded by the same judge, with `--baseline` setting a finished search scan of the same questions and judge beside it. A row whose sources include one of SealQA's own pages, cited or only read, is marked leaked and left out of accuracy; cost is shown only where a backend states it. The latencies quoted for each answer backend are the medians from its run on 300 SimpleQA questions on 2026-11-01, graded by `openai:gpt-4o`. `PRICING.md` gains an Answer section.
- `answer()` as a tool for an agent framework. The Claude and OpenAI `WebRouterTools` take `"answer"` in `methods` and serve `web_router_answer`, sent to `answer_provider`, else to `provider` when it answers, else to the router's default answer backend; with none to use, building the tools raises `NoAnswerProviderError`. LangChain gains `WebRouterAnswer` (`web_answer`). The model sends only the question and reads the answer whole with its citations, each snippet cut to `result_chars`; `routing_guide()` gains a paragraph for it when it is exposed. It is never exposed by default, since every answer backend needs a key and bills each call, so the default tools, the guide and the agent benchmark are unchanged.
- The MCP server's `answer` tool, its twenty-first: the same call as `answer()`, shaped to fit a context window with the answer first, each citation's `field` marker kept, and a handle for `fetch_raw`. `provider` is optional, and only the configured answer backends are offered; unnamed, the router's `auto` tries them cheapest first. The capabilities resource keys its backends as `answer`, and `unlock` lists the ones a key would add.
- Perplexity as an answer backend (`perplexity`): its Agent API at the `fast` effort, one call to `/v1/responses` answering in about two seconds. Maps `include_domains` or `exclude_domains` (its `search_domain_filter`, an excluded domain prefixed `-`; both together are refused before the call), `recency` and `country` (`user_location`) through the `web_search` tool, set only when a filter is; `locale` is refused. The answer cites inline as `[N]`, and each source it cites carries its marker in `Citation.field`. An `incomplete` response is `partial`. Verified live.
- You.com as an answer backend (`you`): its Answer API on `api.you.com`, answering in about two seconds. Maps `include_domains`, `exclude_domains` and `country` to its own fields and `recency` to `freshness`; it takes one domain list, so asking for both raises before the call, and `locale` is refused. Its citations are only the sources the answer cites, marked `[[1, 2]]`; each carries its marker in `Citation.field` and its title from the pages considered. Verified live.
- Parallel as an answer backend (`parallel`): its Chat API (beta) with the `lite` model, answering in about six seconds, the fastest model whose `basis` ties its sources to the answer. Each citation carries the basis's `confidence` in `extra`; a `finish_reason` of `length` is `partial`. The Chat API takes no source filter, so every option is refused. Verified live.
- Exa as an answer backend (`exa`): its Answer API, answering in about 1.3 seconds with its stated cost in `raw`. The answer cites inline as `[N]`, numbering its citations from 1, and each cited source carries its marker in `Citation.field`. No option is mapped: the API has no source filter, and `userLocation` showed no clear effect, so `country` is refused. Verified live.
- Linkup as an answer backend (`linkup`): its Search API with `outputType: sourcedAnswer`, answering in about a second. Maps `include_domains`, `exclude_domains` and `recency`, sent as `fromDate` that far back from today; `country` and `locale` have no Linkup field and are refused. Its sources are every page read; `includeInlineCitations` is always sent, so the answer marks the ones it rests on as `[N]`, and each carries its marker in `Citation.field`. Verified live.
- Brave as an answer backend (`brave`): its Answers API, `POST /res/v1/chat/completions` with `model: brave`, answering in two to three seconds. It returns its sources only on a streamed call with `enable_citations`, so the router streams it and reads the whole stream; the answer is the text with Brave's `<citation>` and `<usage>` tags taken out, and each citation tag becomes a `Citation`, in order, its `number` and its span in the answer in `extra`. `raw` keeps the stream's events, the `<usage>` tag with the call's stated cost among them. It reads `BRAVE_ANSWER_API_KEY`, a key on Brave's Answers plan, separate from `BRAVE_SEARCH_API_KEY`. No option is mapped: the API has no source filter, and `language` showed no effect, so `locale` is refused. Verified live.

### Changed

- The `evals` extra now allows openai 3 (`openai>=1.0,<4`), and the lock moves to openai 3.45.0 and pyarrow 26.0.1 (25.0.1 stays for Python 3.10, which pyarrow 26 no longer supports). openai 3 uses HTTPX2 and no longer installs `httpx`; web-router still declares `httpx` itself, so nothing else changes. The Parallel answer backend's docs link points at its Chat Completions reference, since the old Chat API guide is gone.
- The `max_results` description, in `SearchRequest`'s JSON schema and the MCP `search` tool, now steers an agent to 5 to 10 results instead of one. The README's "Wrapping `search` for your own agent" shows how to pin the number instead.
- `auto` now moves to the next backend when one answers with nothing usable, as it does on an error: a search with no results and no `answer`, or an extract whose every document is blank. A document's page status is not read, since only some backends report one. When every member answers empty, the first empty answer comes back, naming its backend, rather than an error. A call that ends empty has tried every backend that can serve it, one after another, and each one you hold a key for bills for it. `provider_config={"auto": {"fallback_on_empty": False}}` returns the first answer, empty or not; the MCP server has no such switch. `max` is unchanged.
- Nimble's `samples` moved out of `Template.extra` into the typed `Template.samples`; a caller reading `template.extra["samples"]` reads `template.samples` now.

### Fixed

- An error whose exception has no text -- httpx's read and connect timeouts -- now names its type instead of ending blank: a timed-out answer read `answer failed: ` and now reads `answer failed: ReadTimeout`. The same for every method's wrapped failure and the judge's.

## [0.8.0] - 2026-10-28

### Added

- AWS AgentCore Web Search as a search backend (`agentcore`), through the caller's own AgentCore Gateway, set in `AGENTCORE_GATEWAY_URL`. Requests are SigV4-signed with botocore's usual credential chain, for the region in the gateway's hostname; botocore comes with a new `aws` extra, which `all` includes. Maps `max_results` (at most 25), `include_domains` and `exclude_domains`; on a target older than connector 1.2.0, which takes no filters, the domain options raise rather than being dropped. A date range goes through `provider_options["filters"]["publishedDateFilter"]` and merges with the mapped domains. `auto` tries it last, after DeepSeek, so no existing call changes backend. Setup and teardown: `docs/agentcore-setup.md`.

### Fixed

- Screenshots on Anchor are PNG, as on every other backend. ## [0.7.0] - 2026-10-26

### Added

- Templates, a sixth method: `WebRouter.run_template(name, inputs, provider=...)` runs one of a vendor's saved, site-specific extractions (Nimble's Extract Templates today) on one page and returns the record it parsed in `TemplateResponse.data`, `templates(provider=...)` lists one page of the vendor's catalogue as a `TemplatePage`, and `template(name, provider=...)` describes one as a `Template` with the JSON Schema of the inputs a run takes and the record it returns; each has its async twin. A template's inputs are its own -- a URL for some, an id, a slug or a search term for others -- which is why this is a method rather than an option on `extract`, and its name belongs to one vendor, which is why `provider` is required and there is no template `auto`. `format` asks for the page beside the record as `markdown` or `html`; unset, no page comes back. A run the backend could not complete, a page the site answered with 4xx or 5xx, or a parse that failed raises `ProviderError` with the reason, never an empty record; an unknown name raises the new `TemplateNotFoundError`. Nimble is the first backend (`NimbleTemplateProvider`, installed by `[extract]`, verified live), with `TemplateProvider` to add another and `register_template_provider()`, `available_template_providers()` and `configured_template_providers()` beside the other registries. The MCP server adds `templates`, `template` and `run_template`, which alone require `provider`, carry handles for `fetch_raw`, and are keyed as `template` in the capabilities resource.
- `contracts/<method>/<provider>.json`: for every provider, the wire fields each option value sends, read from the provider's own code by `make contracts`, beside the vendor's reference pages, where each mapping was verified (live or in the docs) and the vendor's options no mapping sends. CI fails when a contract no longer matches its provider or leaves a hand-written field empty, so a mapping cannot change without its contract. Extract Template backends have one too. [AGENTS.md](AGENTS.md#provider-contracts) says how to start one.
- `max`, an extract provider that sends the request to every backend `auto` would try, all at once, and returns the first document back -- `WebRouter(Provider.MAX).extract(url)`, with `response.provider` naming the backend that answered. Every fetch it starts is billed by its backend, so it costs up to one extract per configured backend per URL -- most backends take one URL per request, and a loser keeps fetching after the winner returns -- and is never the default. Only a document wins: a backend that refused, could not be built or returned nothing is its own loss, and when every one loses the error names each reason. `provider_config={"max": {"hedge": 0.8}}` runs the first member alone for that long and starts the rest only if it has not answered, so most one-URL calls stay at one fetch; a first member that fails early, or answers only part of the list, starts the rest at once. The hedge covers the first member's whole call, so it does not cap the cost of a multi-URL request. The members are `auto`'s: a `chain` or `members_config` set under `"auto"` in `provider_config` applies to `max` too, unless its own `"max"` entry sets one. `format` routes the same way, and the sync router's `close()` waits for a race's losers before shutting their clients while the async router cancels them. `max` joins `auto` in `BENCHMARK_EXCLUDED`, and the MCP `extract` tool offers it under `provider` with its cost in the description.
- `WebRouter.benchmark_extract()` and its async twin: the same URLs fanned out across several extract backends at once, through the public `extract` path, one `ExtractBenchmarkRun` per provider in an `ExtractBenchmarkReport` -- measured facts only, as `benchmark()` reports for search. A backend that fails, cannot return the format, has no credentials or runs out of the comparison's `timeout` (`BENCHMARK_EXTRACT_TIMEOUT`, 120 seconds) is its own row's error, and a call that fetched some URLs and not others is an answered row whose response says which. `BenchmarkRun` and `BenchmarkReport` now share a base with the extract pair; their fields and behaviour are unchanged, except that a row for a backend that could not be built reports a latency of exactly zero on the async router too.
- `benchmarks/providers/extract.py`: every configured extract backend on the same URLs, tabulated per backend (pages returned with text, empty, failed, timed out, refused, latency, median length) and per category, with a suggested `auto` extract order. Two URL sets ship under `benchmarks/providers/urls/` -- `general` (455 URLs) and `social-pdf` (908 URLs), URL lists sampled from public pages -- and `--urls` takes a CSV of your own. The scan writes `run.json` before its first call and each URL's rows as it finishes, so one that dies keeps what it paid for, and `--combine` on that folder alone reports the rows it fetched against the URLs asked. `examples/compare_extract_providers.py` shows the method on one URL.
- `WebRouter.classify()` and `WebRouter.execute()`, an opt-in spike (unchanged unless you pass `decider=`). `classify(query)` asks a decider one set of questions (tool, recent, coverage, well_scoped) and turns the labels into a `Route`: the method and the auto chain to run it on, searching nothing. `execute(route)` runs it. Passing `urls` routes to extract and `output_schema` to research without asking; a decider that fails, or answers below 0.5 confidence, gives today's default, search on the default chain, with `Route.fallback` saying why (`decider_error`, `low_confidence`, `no_url`, `no_backend_for_method`). The decider is swappable: `WebRouter(decider=...)` takes `"keywords"` (simple keyword rules, keyless, with fixed confidences that are not measured; a research or browse pick sits below the threshold, so it falls back to search), `"jev"` (TypeSafe's Jev, reading `TYPESAFE_API_KEY`), `"llm"` (a chat model with structured outputs over any OpenAI-compatible API, with the `evals` extra, taking `api_key=` or reading `OPENAI_API_KEY`; its version carries a hash of its prompt and schema, `gpt-4.1-mini+p<8 hex>`), a name given to `register_decider()`, or any object with `decide()` and `close()`. `decider_config=` passes constructor kwargs to a decider given by name, as `provider_config=` does for backends. Every built-in decider reports confidence on Jev's normalized scale, `(p - 1/n)/(1 - 1/n)` (`normalized_confidence()`), and the llm decider scales its probabilities to sum to 1 before they are checked; an answer it cannot read takes the `decider_error` fallback. A decider that raises anything, not only `ProviderError`, takes the `decider_error` fallback. Exception types a decider names in its `passthrough` attribute propagate instead of becoming a default route.
- Browser Use now maps `output_schema`, `max_steps` and `allowed_domains`, each checked against a live task on 2026-10-21; they were refused before. The schema is sent as Browser Use's `structuredOutput` and the answer comes back as `structured`; an answer that is not JSON stays in `answer`. `auto` can now serve a browse call that sets any of the three, through Browser Use.

## Alpha snapshot - 2026-10-08

The first alpha snapshot, shared with alpha users. Not a published release:
the next published version will be above it.

- **Five methods behind one interface:** `search`, `extract`, `research`
  (agentic, minutes rather than seconds), `open_browser` (a browser session you
  drive, with page actions built in) and `browse` (a hosted browser agent's
  task). Each call behaves the same whichever backend serves it.
- **Many backends,** from Nimble, Tavily, Exa, Brave, Perplexity, Parallel,
  Linkup, You.com, WebIQ, Firecrawl, Oxylabs, Bright Data and Jina Reader to
  Steel, Browserbase, Hyperbrowser, Anchor, Browser Use, Skyvern and a local
  Chromium. Several need no key at all.
- **`auto`,** the default for every method: it tries the backends you hold keys
  for, then the keyless ones, and routes each request to a backend that can
  serve it. Pass a `chain` to choose your own order, per method.
- **An MCP server** (`web-router-mcp`) exposing every method as tools, including
  `browser_*` tools that drive a session, for Claude Code, Claude Desktop,
  Cursor and other MCP clients.
- **Agent integrations:** tools for the Claude and OpenAI APIs, and for
  LangChain, with a routing guide that tells a model which tool fits which need.
- **Benchmarking and evaluation:** `benchmark()` compares backends on the same
  query, `evaluate()` scores their accuracy on a question set with an LLM judge,
  and `benchmarks/` holds the scripts to run both at scale.
