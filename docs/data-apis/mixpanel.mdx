## Setup

| Variable | | What it is |
|---|---|---|
| `MIXPANEL_SERVICE_ACCOUNT_USERNAME` | required | a Mixpanel service account's username (Organization settings &gt; Service Accounts), granted the project to read |
| `MIXPANEL_SERVICE_ACCOUNT_SECRET` | required | that service account's secret, the Basic auth password |
| `MIXPANEL_REGION` | optional | Query API server for the project's data residency: mixpanel (US), eu.mixpanel (EU) or in.mixpanel (India). Default `mixpanel`. One of `mixpanel`, `eu.mixpanel`, `in.mixpanel`. |
| `MIXPANEL_EXPORT_SERVER` | optional | Raw export server for the same residency: data (US), data-eu (EU) or data-in (India). Default `data`. One of `data`, `data-eu`, `data-in`. |

Put them in your environment or `.env`; [Data APIs](/vendors) covers the other ways.

## Notes

- Every call needs project_id (the number in the project's settings and URL); a project with data views also needs the global view's workspace_id.
- Rate limits are tight: the Query API allows 60 queries per hour and 5 concurrent per project; raw export allows 60 per hour, 3 per second and 100 concurrent. 429 when exceeded.
- Dates are yyyy-mm-dd and inclusive at both ends. Query results use the project's timezone; raw export reads dates as UTC for projects created from 2023.
- Several inputs are JSON encoded into one string: event lists ('["signup","purchase"]'), distinct_ids, values and filter_by_cohort. Filters (where, born_where, on) use Mixpanel's segmentation expression syntax, e.g. properties["&#36;os"]=="Linux".
- The region and export_server settings must name the same residency as the project; a project only answers on its own servers.
